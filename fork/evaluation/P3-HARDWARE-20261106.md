# P3 verification on the owner's Mac, 6 November 2026

**The published p3 installation passes the frozen tool-name tests and all three
JSON-plus-tools integration cases. One JSON Schema array case remains broken.**
This is an independent Mac verification of the published fork, whose original
JSON/tool proposals come from ncphri's #3800 and #4222. It is not a claim that
either original PR alone was tested on Metal or that all JSON Schema rules work.
No upstream PR, issue or comment was published.

## Test identity and activation

The owner installed p3 after instructions to remove all three mask variables.
The API reports engine `0.1.57.3-metal`, a loaded
`qwen3.8-flash-next-unsloth-ud-q4_k_xl`, Apple M1 Ultra, 128 GiB RAM, context
262144 and one serving slot. An independent synthetic diagnostic with an unused
name containing a dot receives HTTP 400 and the strict name-gate message. This
confirms active protection, not just advertised masking capability.

No SSH or process-environment inspection of the owner's Mac occurred. Therefore
actual absence of ENV is based on the owner-managed setup, not remotely attested.
The p3 source and separate installed ARM dependency/method tests prove that the
default requires no mask ENV. Runtime source and weight/tokenizer file hashes
are not independently attested through the API. Published p3 build provenance
identifies source `b6687e44ce4a5f8a783c65ff459692a244a8dadc`.

The tool suite (58 requests) ran first, then the JSON suite (55). Both use the
previously frozen suite, sampling, order and exact canonical request-body hashes.
Both suites target `/v1/chat/completions` with reasoning effort `none`: the tool
suite uses SSE, JSON uses non-streaming replies. Responses/Anthropic and enabled
reasoning are not actual-model coverage of this run. No hidden retries, tool
execution, client configuration changes or service restarts were performed. Reported identities stayed stable within both runs.
The tool generation counter rose by 58; JSON by 52 for its 55 HTTP requests,
which include three expected pre-generation HTTP 400 negative controls. The
activation diagnostic is separate from the 113 benchmark requests.

The tool runner differs from the earliest baseline only in its later privacy
allowlist for nested status exports; the individual metadata hashes retain that
history. Its workload and scoring are unchanged. The JSON runner, transport,
suite and client jsonschema 4.26.0 match the frozen JSON baseline.

## Functional comparison

| Outcome | Unpatched | P1 with flags enabled | P3 owner setup |
| --- | ---: | ---: | ---: |
| Targeted unknown-name failures | 10/10 | 0/10 | **0/10** |
| Additional unknown-name failures | 3/5 | 0/5 | **0/5** |
| Ordinary control unknown names | 0/10 | 0/10 | **0/10** |
| JSON-format stress passes | 3/10 | 9/10 | **9/10** |
| HTTP 200 responses violating schema | 6 | 1 | **1** |
| JSON-plus-tools integration passes | 0/3 | 1/3 | **3/3** |
| Ordinary JSON/text control passes | 6/6 | 6/6 | **6/6** |
| Invalid-request controls correctly rejected | 3/3 | 3/3 | **3/3** |

All fifteen tool stress/additional requests return one declared call with valid
arguments and the intended synthetic operation. No raw XML call text, rejected
unknown names or missing calls were observed. SQL comparisons accept only the
optional trailing semicolon; the literal scorer remains preserved. The tool
suite's ordinary controls stay at 9/10 exact matches because of that pre-existing
semicolon difference, not a new tool error.

The root-array JSON stress case is a format-only pass: an explanatory error
object satisfies json_object while refusing the contradictory requested array.
This is not a useful-business-answer guarantee. The remaining array case still
returns `{"values":[1,1]}` despite minItems=3 and uniqueItems=true. The earlier
audit reproduced unsupported uniqueItems compilation and fallback; p3 does not
add support or full post-validation without its optional dependency.

## JSON plus tools: observed fixed behavior

| Case | P1 outcome | P3 outcome | P3 client total |
| --- | --- | --- | ---: |
| Automatic tool selection + JSON schema | HTTP 400 mask-width error | Valid sql_query call | 1.374 s |
| Required tool selection + JSON schema | Valid call | Valid sql_query call | 1.348 s |
| Final JSON after synthetic tool result | HTTP 400 mask-width error | `{"result":1}` | 1.049 s |

The old mask-width error did not occur. The final-answer fixture contains a
synthetic prior tool result; no SQL was executed and this is not a live database
round-trip benchmark. The previous failing P1 cases took about 64 seconds;
those failures are not equivalent successful-workload timings. P3 JSON ran after
a full tool suite on the same process, which had warmed its tokenizer/name-guard
state. These single integration observations do not establish a causal cold-start
speedup or isolate the effect of a single patch.

## Warm-cache performance

Each workload has ten measured repetitions after a separate excluded warmup.
All normal control and measured performance answers remain equal to baseline
in content/reasoning, tool names/arguments and finish reason; request IDs and
timestamps are intentionally excluded from equality. JSON performance values
also match exactly. Completion and cached-token counts match within workloads.

| Workload | Unpatched median | P3 median | Total change |
| --- | ---: | ---: | ---: |
| Tool suite: text, no tools | 0.985 s | 0.992 s | +0.73% |
| Tool suite: normal tool call | 0.689 s | 0.692 s | +0.42% |
| Tool suite: longer context | 1.268 s | 1.273 s | +0.39% |
| JSON suite: text, no format | 0.838 s | 0.833 s | −0.67% |
| JSON suite: json_object | 1.903 s | 1.947 s | +2.35% |
| JSON suite: json_schema | 1.911 s | 1.959 s | +2.54% |

Tool-suite decode medians change between −0.85% and −0.26%. JSON-suite decode
medians change between +0.16% and −2.24%. These small observed differences are
below the predeclared initial review thresholds; they are not proof of zero
overhead, statistical equivalence or causation. Client times include transport;
server decode timing is retained separately. Draft acceptance differs slightly
in the tool suite. No cold-cache A/B/A sequence, maximum-context, concurrent,
other-GPU or other-model claim is made. JSON is non-streaming, tool tests use SSE;
JSON client latency is not called TTFT.
